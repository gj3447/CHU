# CHU 개념에서 CHU_OS로 넘기는 계약 v1

2026-10-12 · SECONDARY_AI · 구현이 지켜야 할 제안 계약. 철학의 모든 개념을 OS 타입으로
환원하지 않는다. CHU_OS는 이 문서의 commit·path·hash를 고정해 어떤 버전을 구현하는지 밝힌다.

| 계약 | 구현에서 확인할 것 | 실패 예 / 완료를 위한 증거 |
|---|---|---|
| I01 내용/참조 구분 | raw bytes CID와 가변 handle binding을 구분 | 이름 변경으로 내용 정체성을 바꾸거나 유사도만으로 합치는 경우 거부 |
| I02 역할 있는 관계 | n항 관계의 역할·순서·중복 참여 보존 | 인코딩 왕복 및 참여 순서 변경의 음성 대조군 |
| I03 상태/사건 구분 | 같은 결과 상태의 여러 사건, 가능한 분기와 실제 사건 보존 | A→B→A, 같은 끝점의 다른 요청, no-op 사건 |
| I04 관측 범위 명시 | snapshot과 질의 조건, 투영의 정보 손실을 명시 | 화면 경로를 원본 ID로 쓰거나 읽은 판본을 숨기는 경우 |
| I05 실행 주체/권한 | 서술된 actor와 인증·인가를 구분 | 기록에 이름이 있다는 이유로 실행시키지 않음 |
| I06 실패의 의미 | 실패/거부/시간 초과/재시도와 commit 결과를 구분 | 부분 commit, 중복 사건, stale overwrite 검사 |
| I07 이론/구현 연결 | 모델 버전·증명 가정·실행 입력을 보존 | Lean PASS로 실제 스토어·LLM·VM 결과를 대신하지 않음 |

위 I01–I07은 이 문서의 ID이며 기존 Lean 문서의 I1–I5와 다른 범위다.
물리 backend, 스케줄러, 부팅 방식, ABI는 CHU_OS가 선택한다. 인지의 충분조건·의식·
우주의 존재론은 OS 테스트의 합격 조건으로 슬쩍 넣지 않는다.

기존 `spec/`, `os/`, `plan/`, 프로토타입은 분리 시점의 구현 자산이다. `canon/`과 `lean/`의
정본은 CHU에 남긴다. 새 OS 저장소에 검증을 위한 사본이 필요하면 upstream pin과 byte
검증으로 관리하며 독립 철학 정본으로 편집하지 않는다. CLI와 역사적 IRI/task ID는 이름을
바꾸기 위해 재발급하지 않는다. 실제 이관 범위는 [분리 기록](../docs/CHU_CHU_OS_REPOSITORY_SPLIT.md)에 있다.
